## 已确认问题

### 1. P2：UI 按需加载缺少并发去重及关闭取消

位置：`source/assets/scripts/manager/UIMgr.ts:39–49`，以及 `close` 的第 79 行。

`open` 仅在等待资源之前检查是否已打开，等待期间没有登记打开请求。两个并发请求都会实例化界面，后一个覆盖 `_openedUI` 中的前一个引用；随后关闭只能销毁一个节点。加载中调用 `close` 也不会取消请求，资源到达后仍会弹出界面。

验证：通过现有测试加载器执行实际 UIMgr，仅替换资源加载与节点接口。两次并发打开创建了 2 个节点，关闭后只销毁 1 个；另一次加载中关闭的界面，在加载完成后 `isOpened` 仍为 true。

影响范围：当前启动会预加载 UI，普通流程不一定触发；新增按需加载界面、重试或快速导航时会触发。建议用按界面名记录的 pending 请求合并并发打开，关闭时使请求失效，等待后检查请求与管理器生命周期。补充并发打开、加载中关闭、失败后重试测试。

### 2. P3：组件异步实例化在拥有者销毁后永久等待

位置：`source/assets/scripts/custom_engine/CustomComponent.ts:42`。

资源回调发现组件失效时直接 return，没有 resolve/reject。实际执行该方法，加载中销毁组件，再触发成功回调，Promise 在后续事件循环中仍未结束。等待它的流程可能无法解除忙碌状态。

当前业务脚本搜索未发现调用这个扩展方法，因此属于尚未触达的公共工具缺陷，不应夸大为当前关卡故障。建议明确取消结果或携带原因的 reject，并检查父节点有效性；避免无原因的 reject。

### 3. P3：ArrayUtil.remove 声明返回 boolean，删除成功却返回 undefined

位置：`source/assets/scripts/util/ArrayUtil.ts:16–22`。

失败分支返回 false，成功 splice 后未返回 true。将来调用者按返回值判断删除结果时，会把成功当作失败。现有调用点 `ShelveLocker.ts:63` 不读取返回值，当前解锁流程没有因此受影响。建议补齐成功返回值及成功/未找到两个用例。

### 4. P3：计时器 ID 达到上限后持续复用 0

位置：`source/assets/scripts/manager/TimeMgr.ts:38–39`。

超过上限时只重置局部 id，没有重置 nextId，后续申请都会得到 0；Map 覆盖引用后无法正确取消原回调。当前检索到业务使用的是 `TimeMgr.delay`，未发现 `setTimer` 调用，优先级低。建议采用不冲突的 ID 分配方式，并验证同时存活的计时器不会互相覆盖。

## 维护性改进：不等同于已发生故障

- 类型边界：GameMgr.goodsData 初始为 `{}`，ShelveBase.GoodsInfo 返回 Object，UIMgr 的注册表也是 Object；Stage 多处需要断言 number[]。已有 GoodsData 类型可以直接复用，优先补这些关键边界，无需全面改名或增设抽象层。
- 结果类型：GameSave.ActionResult 的 ok 是 boolean，value/reason 都可选，允许表达无 reason 的失败。可以逐步采用以 ok 为判别字段的联合类型，保留现有事务与存档格式。
- 职责集中：Stage 465 行同时承担关卡创建、布局、技能执行、结算及特效；GameMgr 309 行包含局内状态和拖拽交互。先给复杂商品选择规则加类型或提取纯计算，再考虑拆分；文件行数本身不构成缺陷。
- 小范围重复：UISetting 与 UIPause 的 changeSetting 流程相近，可共享提交设置与恢复失败状态的函数，无需为此引入大型 UI 继承体系。
- 生命周期：UIMgr 订阅 EventMgr、AudioMgr 订阅 game hide/show 后没有对应销毁解绑。当前单入口场景下不直接证明故障；未来增加场景切换或管理器重建时应测试并补全生命周期。
- 类型诊断：当前 strict 为 false；重新检查仍有 183 个原有诊断，包含引擎声明重复和缺少类型等。应先梳理项目根 cc.d.ts 与 Creator 生成声明的关系，再逐步收紧业务类型，不应使用关闭检查或 skipLibCheck 代替解决。
